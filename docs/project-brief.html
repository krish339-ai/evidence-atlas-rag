One sentence, a clear scope

My RAG app helps AI learners answer research questions from the RAG, Self-RAG, and CRAG papers in a web app, targeting 95% faithfulness and responses within 15 seconds.

01 / Name the corpus

Three specific English research papers, with source links and pinned versions. This is a defined collection we can inspect and evaluate.

02 / Measure faithfulness

The target is 95%: supported factual claims divided by evaluated factual claims. We track refusal correctness and answer coverage separately so abstaining cannot inflate the score.

03 / Set a latency ceiling

The proposed target is a query response within 15 seconds after indexing. Measure end-to-end latency, report misses, and exclude initial ingestion from this query target.

Targets, not achievements. Neither 95% live-answer faithfulness nor the 15-second live response target has been established. Local retrieval speed is not evidence of live-model speed.

The six-field RAG framework

Initial decisions, kept to one or two sentences per field.

FieldEvidence Atlas RAG decision
Use caseHelp AI learners ask and compare questions about research methods, findings, and limitations through a web application, with paper-and-page citations and targets of 95% faithfulness and responses within 15 seconds after indexing. Missing or unsupported evidence leads to an explicit insufficient-evidence response; ambiguous comparison criteria call for clarification.
CorpusStart with three English-language research PDFs: Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks, Self-RAG, and Corrective Retrieval Augmented Generation. The authors’ papers, obtained from arXiv with recorded versions and source links, are the source of truth.
Ingestion + cleaningLoad the starter PDFs or user-uploaded text-based PDFs, extract text page by page, and remove repeated headers, footers, and formatting noise. Preserve document identity and page references for citations; scanned PDFs require OCR before upload.
Ingestion + freshnessUse a fixed snapshot of the three papers for reproducible evaluation, with manual refresh when we adopt a newer version or replace a document. Updated content becomes searchable after successful reindexing; automatic monitoring for new versions is outside the initial scope.
Chunking + embeddingSplit each page into chunks of up to 1,400 characters, with 200 characters of overlap, to retain local context and page references. Use text-embedding-3-small as the initial live embedding model, then evaluate whether this model and chunk configuration retrieve the expected evidence.
RetrieveUse LangChain’s in-memory vector store now, with Pinecone as an optional future backend, and combine live semantic similarity with BM25 keyword search through reciprocal rank fusion. Retrieve 6 passages, balance coverage across selected papers for comparisons, and allow one expansion to 12 passages when the initial coverage check is weak.

Retrieval design decisions

Choose chunks and embeddings together

The 1,400-character chunk size, 200-character overlap, and live embedding model are an initial configuration to test, not a proven optimal match. Character counts are not token counts; evaluate evidence recall, boundary loss, and latency rather than assuming embedding dimensions alone determine the right chunk size.

Combine semantic and keyword retrieval

The live design combines semantic vectors with BM25 to cover paraphrases and exact terms. Reciprocal rank fusion merges rankings; it is not a separate model-based reranker. A second-stage reranker has not been implemented or measured.

Design the “I don’t know” path first

LangGraph checks retrieval coverage and can expand once before declining. The initial check uses lexical overlap, which is only a routing heuristic; live generation also checks citation IDs, exact supporting quotes, selected-paper coverage, and a model-based evidence audit before displaying an answer.

Local mode returns verbatim source excerpts and labels them as such. Shared keywords do not establish answerability: local mode may still retrieve excerpts for an unsupported request. Live refusal and faithfulness must be evaluated separately.

A real, reproducible starting corpus

  1. Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks — Lewis et al.; 2020 paper, arXiv version 4 (April 12, 2021).
  2. Self-RAG: Learning to Retrieve, Generate, and Critique through Self-Reflection — Asai et al.; arXiv version 1 (October 17, 2023).
  3. Corrective Retrieval Augmented Generation — Yan et al.; 2024 paper, arXiv version 3 (October 7, 2024).

PDF page numbers are one-based physical pages, which may differ from printed page labels. The local downloader records SHA-256 hashes; keep the manifest and download instructions in the repository rather than assuming all PDFs can be redistributed.

What counts as evidence of quality?

  • Retrieval: compare a vector baseline against hybrid retrieval at the same top-k, using questions with expected paper, page, and passage anchors.
  • Faithfulness: human-check every factual claim against its cited evidence; divide supported claims by all evaluated factual claims and flag uncertain claims separately.
  • Relevance: score each answer 0 (off-topic), 1 (partially addresses the question), or 2 (directly addresses it); report mean score and answer coverage.
  • Citations: check that IDs resolve, quoted text exists, and the quote supports the whole claim. Exact quote matching alone cannot establish entailment.
  • Fallback: test direct, cross-paper, ambiguous, unanswerable, and adversarial questions; report false refusals as well as unsupported answers.
  • Latency: report end-to-end p50 and p95 after indexing, the percentage above 15 seconds, and provider/model versions. Per-request timeouts are not an enforced 15-second total deadline.

Current local evaluation files: evaluation/questions.json, evaluation/results.json, and evaluation/REPORT.md. The local set measures retrieval and routing, not live-answer faithfulness.

Configure live mode and optional storage

For live generation, keep VECTOR_BACKEND=memory and configure the model provider. Pinecone is optional and its live connection remains unverified.

For optional Pinecone setup: Open the ignored .env in your local editor. Set EVIDENCE_ATLAS_MODE=live, VECTOR_BACKEND=pinecone, MODEL_API_KEY, PINECONE_API_KEY, and the existing PINECONE_INDEX_NAME; confirm provider model names and URLs. Never paste keys into chat or put them in browser storage or the public repository.

The existing index must accept externally generated dense vectors with cosine distance. EMBEDDING_DIMENSIONS must match both the model and index (1536 for the initial default); the app probes the output size before uploading documents. It does not create or reconfigure paid resources.

PINECONE_NAMESPACE_PREFIX=evidence-atlas receives a fresh random suffix for every collection. Pinecone persists vectors and passage text; clearing the local collection deliberately leaves those remote records intact. No unrelated namespace is used. See docs/PINECONE.md for the full setup, persistence, cleanup, and live-verification checklist.

Current implementation and boundaries

The initial build includes a local landing page, PDF collection controls, a question workspace, a source-excerpt reading matrix, page-level evidence inspection, exportable research trails, and a LangGraph retrieval flow. These are initial design choices, with verification results recorded separately in the evaluation report and README.

Live semantic retrieval and generated answers require model configuration. The offline demo uses deterministic lexical test embeddings and exact source excerpts; it does not impersonate a language model or claim semantic understanding.

PDFs and the local collection state stay in server memory and must be reloaded after restart; optional Pinecone vectors and passage text persist remotely, but do not restore the collection by themselves. There is no OCR, automatic version monitoring, persistent user accounts, hosted deployment in this first version.

Existing accounts and future storage

The default backend is VECTOR_BACKEND=memory; Pinecone is an optional future integration. A configurable adapter is implemented with mock tests; it validates an existing dense cosine index and embedding dimension, then uses a unique evidence-atlas namespace per collection. No Pinecone index was created or reconfigured, no unrelated namespace was touched, and live access has not been verified. Remote LangSmith tracing is not configured.

Next validation steps

Configure a live model with the in-memory backend, review generated claims against the papers, and measure faithfulness and response latency. Add held-out questions before drawing conclusions about general quality.
